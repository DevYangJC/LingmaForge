> 审查视角：十年经验后端工程师
> 审查范围：`lingmaForge-backend/` 全量源码
> 审查日期：2026-07-08

## 0. 总体评价（先说结论）

这是一个**技术选型先进、AI 编排设计有想法，但工程化与安全防线严重缺位**的项目。

**亮点**：LangGraph4j 的 StateGraph 图编排 + 模板方法节点 + 策略式 Agent 路由，这套 AI 流水线骨架是经过思考的，不是堆 CRUD。Java 21 + Spring Boot 3.5 + LangChain4j 1.17 的栈很新，方向对。

**短板**：作为一个"对话生成应用"平台，**鉴权完全裸奔、任意 ID 越权、宿主机直接跑 npm 构建（RCE 风险）、API Key 硬编码进 classpath**——这四条任意一条进了生产都是事故。工程层面，双写无事务、进程无回收、线程池无上限，跑起来是能跑，扛不住量也扛不住异常。

一句话：**AI 部分像样，工程地基是漏的**。下面展开。

## 1. 技术栈与框架分析

### 1.1 依赖全景

| 维度 | 选型 | 版本 | 评价 |
|---|---|---|---|
| 语言/运行时 | Java | 21 | 虚拟线程可用，但项目未启用 |
| Web 框架 | Spring Boot | 3.5.7 | 主流稳定 |
| AI 编排 | LangChain4j + LangGraph4j | 1.17.2 / 1.8.19 | 选型正确，白盒可控 |
| ORM | MyBatis-Plus | 3.5.15 | 单模块够用 |
| DB | H2(dev) / MySQL(prod) | — | dev 文件模式 + `MODE=MySQL` |
| 文档 | springdoc-openapi | 2.8.10 | 有 Swagger |
| 安全 | **无** | — | pom 无 spring-security |

### 1.2 框架使用方式评价

**LangChain4j 用得对**：`AiServices.builder()` + `@Tool` + `systemMessageProvider` + `maxToolCallingRoundTrips(12)` 是标准用法。流式（`OpenAiStreamingChatModel` / `AnthropicStreamingChatModel`）仅 `CodeGenAgent` 用，符合"代码生成才需 token 流"的判断。

**LangGraph4j 用得对**：`StateGraph` + `AgentState` + `Channel`（LastValue/Appender）+ `addConditionalEdges` 做条件回退，这是图编排的正道，比线性 if-else 强。

**MyBatis-Plus 用得浅**：4 个 Mapper 全 `extends BaseMapper`，**零自定义 SQL**，全 `LambdaQueryWrapper`。好处是简单，坏处是复杂查询只能靠 Java 层堆——目前业务还没到那一步，可接受，但要心里有数。

**Spring Security 完全缺失**：pom 里没有，代码里没有 `SecurityFilterChain`、`@PreAuthorize`、`Authentication`。所有 `/api/**` 默认开放。这不是"还没来得及"，是地基缺口。

## 2. 代码结构与设计模式分析

### 2.1 包结构（按业务域分包）

```
com.lingmaforge.backend
├── workbench/          ← 核心业务（项目CRUD + AI流水线 + 沙箱），唯一有实现的模块
│   ├── ai/
│   │   ├── factory/    ← AgentFactory（模型路由 + AiServices 创建）
│   │   ├── node/       ← 流水线节点（AbstractCodeGenNode 模板方法）
│   │   ├── observer/   ← GenerationContext / StreamEmitter / StreamRegistry
│   │   ├── pipeline/   ← CodeGenPipeline / IterationPipeline（StateGraph 编排）
│   │   ├── service/    ← Agent 接口（策略契约）
│   │   ├── support/    ← PromptLoader 等
│   │   └── tool/       ← @Tool 工具（FileTools / ProjectContextTools / IterationTools）
│   ├── entity/  mapper/  service/  web/
├── common/             ← Result / GlobalExceptionHandler / ControllerLogAspect
├── infra/config/       ← 7 个配置类
├── admin auth billing creative doc/   ← 5 个空壳 Controller，只有 @RequestMapping
```

**结构评价**：workbench 是"大杂烩单体"，其他 5 个模块是占位空壳。现阶段业务还没拆，可以接受；但 `@MapperScan` 只扫 `workbench.mapper`（`LingmaForgeBackendApplication.java:7`），将来 admin/auth 加 Mapper 会漏扫，是个埋点。

### 2.2 设计模式清单

| 模式 | 落点 | 评价 |
|---|---|---|
| **模板方法** | `AbstractCodeGenNode`（`AbstractCodeGenNode.java:18`）：`setupContext` → 业务 → `finally{completeNode}` | 标准且正确，子类只填业务 |
| **策略** | Agent 接口（`RequirementAnalyzer`/`CodeGenAgent`/...）由 `AiServices` 实现，`AgentFactory.resolveModel` 路由模型 | 干净 |
| **工厂** | `AgentFactory` 集中创建 Agent，按阶段路由模型 | 可行，但回退逻辑略脆（见 4.2） |
| **观察者/Emitter** | `GenerationStreamEmitter` + `GenerationStreamRegistry`，按 taskId 查 emitter 直接 push | **命名误导**：不是发布订阅，是"按 key 查找直接调用"的推模式 |
| **配置映射** | `@ConfigurationProperties` record（`LingmaModelsProperties`/`LingmaSandboxProperties`） | 现代，但 `pipeline.max-retry-count` 没纳入，散落 `@Value` |
| **双写** | DB（`lf_project_file`）+ 文件系统（`./workspace/{projectId}/`） | 思路对，但**无事务无补偿**（见 4.4） |

### 2.3 AI 流水线编排（核心设计）

6 节点 + 1 终止节点，条件边回退：

```
START → requirement_analysis → execution_planning → code_generation
      → style_optimization → build_verification →[routeAfterBuild]→ preview_deploy → END
                                                  ↘ (retry≤max) 回 code_generation
                                                  ↘ (retry>max) → ERROR_END
```

- **状态**：`CodeGenState extends AgentState`，单值字段 `Channels.base()`（覆盖），列表字段 `Channels.appender()`（追加，如 `GENERATED_FILES`）。
- **重试上限**：`@Value("${lingma.pipeline.max-retry-count:2}")`（`CodeGenPipeline.java:65`）。实际语义：**回退 2 次，第 3 次构建失败才终止**（`BuildVerificationNode.java:62` 每次失败 +1，`routeAfterBuild` 判 `> max`）。注释与代码一致。
- **并行文件生成**：`CodeGenerationNode`（`CodeGenerationNode.java:102-118`）用 `CompletableFuture.runAsync` + `fileGenExecutor` 并行多文件，`allOf(...).get(300, SECONDS)` 阻塞等待。
- **上下文跨线程**：子线程显式 `GenerationContext.set(...)` 重新注入（ThreadLocal 不继承，处理正确），`finally` 清理。

这套编排**设计上是成立的**，问题全在异常路径与资源回收（见第 4 节）。

## 3. 核心业务流程梳理

### 3.1 生成流程

1. `POST /api/generation/create` → 建任务 + 存 ChatMessage，返回 taskId（`GenerationService.java:109-116`）
2. `GET /api/stream/generation/{taskId}` → 建立 SSE，`executor.execute(runPipeline)` 异步跑流水线（`GenerationService.java:124-160`）
3. 流水线迭代 `graph.stream(inputs)`，节点内通过 emitter 推 `message/file/log/complete/error` 事件
4. `DELETE /api/generation/{taskId}/stop` → 置停止信号

### 3.2 双写

`FileTools.writeFile` → `projectFileService.writeFile`（先磁盘后 DB）→ `emitter.emitFile` 推前端。

### 3.3 沙箱构建

`SandboxService.npmBuild` → 宿主机工作区 `ProcessBuilder` 跑 `npm install && npm run build` → 启 dev server 预览。

## 4. 核心业务存在的问题（按严重度分级）

### P0 严重 —— 上生产前必须修

#### 4.1 【安全】API Key 硬编码进 classpath
- **位置**：`application-local.yml:87,99,112,137`
- **事实**：DeepSeek / DashScope / Moonshot 的真实 `sk-xxx` 作为环境变量**默认值**写进 yml，随构建打入 jar。即使 `.gitignore` 排除，产物里仍有。
- **后果**：密钥泄漏，token 被盗刷。
- **整改**：立即吊销已暴露的 3 个 key；yml 默认值改为空串；只走环境变量/Secret 管理。

#### 4.2 【安全】无鉴权 + 任意 ID 越权
- **位置**：`workbench/web/*Controller.java` 全文无 `userId`/`ownerId`/`@PreAuthorize`
- **事实**：`ProjectController`、`GenerationController`、`SandboxController` 仅凭 projectId/taskId 操作，不校验归属。
- **后果**：任意客户端凭猜测/遍历 ID 即可读写删除他人项目文件、订阅他人 SSE 流、启停他人沙箱。
- **整改**：引入 Spring Security + 用户体系；所有 project/task 操作加归属校验。

#### 4.3 【安全】宿主机 npm 构建 = RCE
- **位置**：`SandboxService.npmBuild:46-69`
- **事实**：在宿主机工作区直接 `ProcessBuilder` 跑 `npm install/build`。AI 生成的 `package.json` 的 `scripts`/`postinstall` 可执行任意命令。
- **后果**：AI 被诱导生成恶意 `package.json` → 宿主机命令执行。
- **整改**：Docker/容器隔离（CLAUDE.md 说 M3 才上，当前是裸跑）；至少限制 `--ignore-scripts`。

#### 4.4 【安全】CORS 全开 + 凭证
- **位置**：`WebConfig.java:13-16`
- **事实**：`allowedOriginPatterns("*")` + `allowCredentials(true)` + `allowedHeaders("*")` + 所有方法。
- **后果**：任意站点可携带凭证跨站请求。
- **整改**：生产环境限定具体域名。

---

### P1 高 —— 影响稳定性与数据一致

#### 4.5 【一致性】双写无事务无补偿
- **位置**：`ProjectFileServiceImpl.writeFile:47-76`
- **事实**：先写磁盘后写 DB，无 `@Transactional`、无补偿。DB 失败 → 磁盘已写、DB 无记录，前端文件树缺失但构建可用。
- **后果**：数据不一致，排查困难。
- **整改**：要么"DB 为主 + 磁盘异步重建"，要么加补偿删除已写磁盘文件。

#### 4.6 【资源泄漏】进程不回收
- **位置**：`SandboxService.execCommand:104-126`
- **事实**：`process = builder.start()`，try-with-resources 只关 reader；`readLine` 阻塞则 `waitFor` 永不执行，**进程泄漏**；异常时无 `process.destroy()`。
- **后果**：每次构建失败残留 npm/node 进程，OOM。
- **整改**：finally 里 `process.destroyForcibly()`；加超时。

#### 4.7 【资源泄漏】沙箱 Map 无驱逐
- **位置**：`SandboxService.sandboxMap:33`
- **事实**：仅 `stopDevServer` 移除，startDevServer 后不停止则永久驻留。
- **整改**：加 TTL/定期清理。

#### 4.8 【线程池】文件生成池无上限
- **位置**：`AsyncConfig.java:51-57`
- **事实**：`fileGenExecutor` 用 `newCachedThreadPool`，最大 `Integer.MAX_VALUE`。突发并行文件生成可创建大量线程。
- **整改**：改 `ThreadPoolTaskExecutor` 设上限。

#### 4.9 【并发】超时不取消子任务
- **位置**：`CodeGenerationNode.java:117-118`
- **事实**：`allOf(...).get(300, SECONDS)` 超时抛 `TimeoutException`，但底层 `CompletableFuture` 未 cancel，子线程 LLM 流继续跑，token 持续计费。
- **整改**：超时后 cancel + 中断；`TokenStream` 底层 HTTP 流也要能中断。

#### 4.10 【并发】停止信号不中断 LLM 流
- **位置**：`CodeGenerationNode.java:173-186`
- **事实**：检测到 `isStopRequested` 后 `streamFuture.complete(...)`，但 LangChain4j `TokenStream` 底层 HTTP 流未中断，LLM 仍计费。
- **整改**：需要 LangChain4j 层面的取消机制。

### P2 中 —— 影响质量与可维护

#### 4.11 【性能】N+1 与冗余查询
- `ProjectFileServiceImpl.readFiles:85-91`：循环逐个 `readFile`，应批量。
- `patchFile:108-128`：已读 content，又调 `writeFile` 内 `findByPath` 再查一次。
- `GenerationTaskServiceImpl`：每次状态更新先 `getByTaskId` 后 `updateById`，应直接 `update(...).eq(taskId)`。

#### 4.12 【质量门禁形同虚设】validateCode
- **位置**：`FileTools.validateCode:113-139`
- **事实**：仅字符串 `contains("export")`/`contains(": any")` + 正则抽 import，无真实 TS 编译。注释里的 `: any` 也会误判。
- **整改**：接入 `tsc --noEmit` 或 esbuild 真校验。

#### 4.13 【异常吞掉】多处静默
- `ProjectServiceImpl.deleteProject:202-203`：`catch (IOException ignored) {}` 完全静默。
- `ProjectFileServiceImpl.sha256:260-262`：`NoSuchAlgorithmException` 捕获返回 null，checksum 失效无告警。
- `SandboxService` 心跳/SSE send 失败仅 debug 日志（`GenerationService.java:153,478`）。
- `BuildVerificationNode.java:68-75`：沙箱异常仅 log 后 return，丢原始堆栈。

#### 4.14 【配置矛盾】模型路由与注释不符
- **位置**：`application-local.yml:160-161` vs `:150-152`
- **事实**：注释说代码生成应用 `deepseek-pro`，实际配 `deepseek-flash`。代码生成走最便宜模型，质量风险。

#### 4.15 【逻辑】客套话清洗误伤合法代码
- **位置**：`CodeGenerationNode.java:332`
- **事实**：正则 `.*[好让为请您我我们这].*` 且 `length < 30` 会误删 `// 我们使用 React 18` 这类合法注释。

#### 4.16 【状态】BUILD_ERROR 写 null 行为不明
- **位置**：`CodeGenerationNode.java:135` → `CodeGenState.BUILD_ERROR` 用 `nullableChannel()`
- **事实**：向 `Channels.base(null)` 写 null，LangGraph4j 对 null 合并未明确，回退时 `buildError` 可能仍非空触发误判。

#### 4.17 【HTTP 语义】业务异常返回 200
- **位置**：`GlobalExceptionHandler.java:40,55,71,85`
- **事实**：业务/参数异常统一返回 `HttpStatus.OK`，只有兜底返回 500。前端无法用 HTTP 状态码拦截，监控告警漏报。

### P3 低 —— 体验与规范

- **空壳模块**：admin/auth/billing/creative/doc 5 个 Controller 是空类（`*Controller.java:11`），但已注册路由。
- **缺失异常类型**：`GlobalExceptionHandler` 未处理 `HttpMessageNotReadableException`/`NoHandlerFoundException`/`HttpRequestMethodNotSupportedException`，均落兜底"系统异常"。
- **MyBatis-Plus 缺插件**：`MybatisPlusConfig.java:21-25` 只有分页，无乐观锁、无防全表操作。
- **无逻辑删除**：实体无 `@TableLogic`，`deleteProject` 物理删除。
- **注释过时**：`AgentFactory.java:235-246` 注释说"注册 writeFile/readFileContext/validateCode 工具"，实际 `CodeGenAgent` 已改纯流式无工具。
- **未使用变量**：`AgentFactory.java:147,180` 的 `int retries` 声明后未传入 builder，模型重试为默认值。
- **心跳单线程**：`GenerationService.java:74-78` 单线程调度所有任务心跳，高并发延迟。
- **CallerRunsPolicy 阻塞容器线程**：`AsyncConfig.java:37` 队列满时 `runPipeline` 在 Servlet 线程同步执行，拖垮容器。
- **prompts 缺对称文件**：有 `iteration-modification-system.txt` 但缺 `iteration-modification-user.txt`（需核对）。

## 5. 整改优先级建议

| 优先级 | 事项 | 工作量 | 阻断生产 |
|---|---|---|---|
| P0-1 | 吊销并清理硬编码 API Key | 0.5d | 是 |
| P0-2 | 引入 Spring Security + 归属校验 | 3-5d | 是 |
| P0-3 | 沙箱 Docker 隔离（至少 `--ignore-scripts`） | 2-5d | 是 |
| P0-4 | CORS 限定域名 | 0.5d | 是 |
| P1-1 | 双写事务/补偿 | 2d | 否（但影响数据） |
| P1-2 | 进程回收 + 沙箱 Map TTL | 1d | 否 |
| P1-3 | 文件线程池加上限 | 0.5d | 否 |
| P1-4 | 超时/停止真正中断 LLM 流 | 2d | 否 |
| P2 | N+1、validateCode、异常吞掉、配置核对 | 3d | 否 |

**结论**：AI 流水线骨架可保留，但 P0 四条不修，这个项目不能上生产。建议先用 1-2 周把 P0 清掉，P1 在首次压测前补齐。
