**Phase 2 关键技术决策与踩坑**：
1. **ChatReplyNode 通过 GenerationStreamRegistry 获取 emitter**（NOT GenerationContext ThreadLocal）——DialogRouter 用 `node_async` 派发到 fork-join 线程，ThreadLocal 不传播，改以 `dialogId` 为 key 从 registry 取 emitter。
2. **`.start()` 同步异常兜底**——NoOpStreamingModel 在 `start()` 内同步抛 `IllegalStateException`（不走 onError 回调），故 `.start()` 必须包在 try 内，与 `future.join()` 抛出的 `CompletionException` 共用同一 catch。两类异常一漏一不漏都会让图崩溃。
3. **`@TestConfiguration` 自动检测污染坑**——`StubChatAgentConfig` 原放在 `com.lingmaforge.backend.ai.dialog`（在主应用 `@ComponentScan(basePackages="com.lingmaforge.backend")` 范围内），被 Spring Boot test support 自动检测并应用到所有 `@SpringBootTest`，导致 NoOp 场景误用 mock AgentFactory。改 `@Configuration` 不够，最终移到 `com.lingmaforge.testconfig`（扫描范围外）才根治。
4. **端点合并**——清单原写 `POST /api/chat/send` + `GET /api/chat/stream/{dialogId}` 两端点；实际改为 `POST /api/chat/{dialogId}/send` 直接返回 SseEmitter。理由：流式回复中"发消息"和"开流"分离会引入竞态（消息已发但 SSE 未连上时 token 丢失）。另补 `dialog`/`messages`/`dialogs` 端点支撑 4-3 持久化。

## 5. Phase 3 — 代码修改子图（接 IterationAgent） ✅

**目标**：用户说"把首页改成蓝色"，走代码修改而非全量重生。

**实现方案**（方案 A — 内联编排，详见 `项目文档/方案文档/Phase3-代码修改子图设计.md`）：

- [x] **5-1 迭代意图解析** — 复用 `DialogRouter` 的 `intent_detection` 节点识别 `MODIFY_CODE` 意图，路由到 `delegate_iterate`。用户修改指令 + 项目上下文（框架 + 文件列表）拼成 prompt 传入 `IterationAgent.modify`，由 Agent 自行用 `searchCode`/`readFileContext` 工具定位目标文件。（2026-08-13）
